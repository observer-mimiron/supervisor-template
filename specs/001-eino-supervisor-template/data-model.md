# Data Model

## Dataset and Case

The human-maintained dataset uses the parent project's `name`, `version`, `description`, `cases` envelope. The loader produces immutable Cases; it never accepts generated expectations or rewrites evaluator rules. Full field contract: [contracts/evaluation.md](./contracts/evaluation.md).

| Field | Meaning | Invariant |
|---|---|---|
| `id` | Stable Case identifier | Unique within dataset version |
| `version` | Case semantic version | Increment when expected behavior changes |
| `category` | `positive`/`negative`/`boundary`/`diversity` | Registered enum |
| `risk_level` | `low`/`medium`/`high` | High risk specifies approval/review expectations |
| `impact_tags` | Human-maintained business/architecture scopes covered by this Case | Deterministic CI selector; not generated or rewritten by Runner/Judge |
| `business_goal` | Human-authored objective | Descriptive, not executable |
| `preconditions` | Fixture, subject and initial state | Registered local fixture only |
| `request_steps` | Chat/approval/resume/cancel/repeat actions | Fixed order; Runner cannot append steps |
| `expected_results` | Response, event order, state and result assertions | Read-only to Runner and Evaluator |
| `forbidden_side_effects` | Disallowed Tools/writes/events | Includes pre-approval write ceiling |
| `evidence_requirements` | Required evidence categories | Structured and redacted |
| `evaluator_rules` | Deterministic rule/version references | Must resolve to registered rules |
| `timeout` | Total Case execution budget | Positive; includes all follow-up operations |
| `retry_budget` | Safe pre-call retries only | Non-negative; unknown outcome is never retried |
| `idempotency_key` | Fixed Case key or deterministic template | Never generated by model |
| `cleanup_policy` | Fixture reset/isolated process policy | Cannot clear state owned by other Cases |

## Runtime Evidence

`RunEvidence` is a sanitized observation record, not a business state owner:

- `run_id`, `case_id`, `case_version`, `code_version`, `trace_id`, `request_id`;
- ordered event references: sequence, event type, terminal marker, safe data keys;
- Tool/worker/step references, risk and approval state, error class and retry decision;
- run/approval/recovery/cancel/terminal state snapshots;
- fixture name, fake write count and resource allow-list;
- elapsed time, deadline outcome and retry count;
- stable evidence reference IDs; no sensitive text or internal file paths.

Existing SSE and `RunEvent` provide most fields; a narrow adapter is needed for fake side-effect counts and Tool evidence not present in SSE. Architecture evidence also includes static package dependency results, since runtime events cannot establish source dependency direction. No SQL evidence is fabricated for the in-memory case.

## Evaluation Report

Each run produces a machine-readable report with dataset and Case versions, code revision, evaluator versions, generated time, run IDs, pass/fail counts, categorized failures, and independent results for each evaluator/assertion. Every failure contains `case_id`, `case_version`, `code_version`, `run_id`, `evaluator_name`, `evaluator_version`, `failed_assertion`, `evidence_reference`, and nullable `human_disposition`. Full user response/Tool payload is omitted by default.

## Optional Judge and Human Calibration

Soft review records carry rubric version, score, risk, finding, evidence reference, confidence, recommendation, human-review flag, model/prompt version, input/output digest and evaluation timestamp. Human dispositions distinguish business expectation, implementation, architecture, evaluator rule, Case data, environment/dependency and Judge errors. A failure enters the dataset only after human confirmation.

## PR Risk Review

A PR review record declares risk (low/medium/high), affected tags, reviewer, decision, rationale, and timestamp. High risk includes changes to Policy Gate, identity/resource authorization, approval, idempotency, state ownership, persistence, external side effects, or dependency direction. High-risk changes run the full dataset and require approval independent of evaluator/Judge output. Missing or uncertain classification is high risk. Failure calibration and PR approval are separate records and decisions.

## Durable execution entities

Durable execution extends the existing model; it does not introduce a generic `state` owner.

| Entity | Authoritative owner | Required fields | Invariants |
|---|---|---|---|
| Run snapshot | Application/Manager through `Repository` | `run_id`, `plan_id`, ordered `steps`, run status, terminal code, error class, `updated_at` | Step count/order and succeeded steps cannot be rolled back; a terminal run is immutable except projection repair |
| Plan step | `ExecutionPlan` | `step_id`, status, attempt, attempt status, idempotency key, result digest/content, error class, `updated_at` | One step is executed at a time; `running` after an owner crash is not assumed safe to retry |
| Run lease | `RunLeaseStore` adapter | `run_id`, random `owner_token`, `expires_at` | At most one non-expired owner; only current owner may release; expiry permits a new owner |
| Checkpoint | `CheckpointStore` | `run_id`, `plan_id`, monotonic version, completed step IDs, resume token | Version is contiguous per run; it is a cursor, not a second state machine |
| Run event | `EventStore` | `event_id`, `run_id`, sequence, type, safe data | Sequence starts at 1 and is contiguous; one public terminal event; duplicate event ID is idempotent |

### State transitions

```text
pending -> running -> waiting_approval -> running
                 -> waiting_reconciliation
                 -> completed | failed | canceled
```

`waiting_reconciliation` is terminal for automatic execution but not a guessed failure: a human or
explicit reconciliation operation must resolve the external outcome. A lease expiry during
`running` may only make the next owner enter this state. Repeated Resume on a terminal Plan reads
the existing events and repairs missing projections without re-running a Tool.

### Partial-write recovery matrix

| Failure point | Durable fact | Resume behavior | Guarantee |
|---|---|---|---|
| Before Tool call | Plan/checkpoint still pending or running | Reclaim lease and execute only if no in-flight marker exists | At-least-once application step; no external call happened is only known before call |
| Tool started, result unknown | Step/Run marked `waiting_reconciliation` when possible | Return `RUN_OUTCOME_UNKNOWN`; never auto-retry | No duplicate side effect, manual reconciliation required |
| Plan saved, checkpoint failed | Plan is authoritative; cursor may lag | Rebuild checkpoint from Plan under lease | Recoverable projection, not atomic across stores |
| Checkpoint saved, event append failed | Cursor exists; public projection may lag | Re-emit missing progress/terminal events with sequence checks | Recoverable projection, not exactly-once |
| Event append succeeded, later state write failed | Event is evidence only; Plan remains owner | Load Plan, avoid treating event as authority; repair projection or surface storage error | No event-driven state mutation |

The planned contract tests inject each boundary and assert an explicit recoverable status. They must
not use event presence alone to infer that a side effect completed.
